# ADR-001: Foundational Architecture, Tech Stack, and Boundary Rules for AutoDrive TestBench

**Status:** Accepted  
**Date:** 2023-10-24  
**Author:** System Architect  
**Deciders:** Core Engineering Swarm  
**Context:** Autonomous Rental Car System (AutoDrive TestBench)

---

## 1. Architectural Style: Clean Architecture

The **AutoDrive TestBench** must validate autonomous vehicle operations, rental state machines, telemetry streams, and hardware-in-the-loop (HIL) / software-in-the-loop (SIL) failure modes. Because hardware integrations, simulation environments, and database engines evolve rapidly, the system adopts **Clean Architecture** (Hexagonal/Ports and Adapters).

The system is partitioned into concentric layers with strict isolation boundaries:

```
+-----------------------------------------------------------------------+
| Frameworks & Drivers (Infra, DB, Message Bus, Hardware/Sim Drivers)   |
|   +---------------------------------------------------------------+   |
|   | Interface Adapters (Controllers, Presenters, Gateways)        |   |
|   |   +-------------------------------------------------------+   |   |
|   |   | Application / Use Cases (Workflows, Ports)            |   |   |
|   |   |   +-----------------------------------------------+   |   |   |
|   |   |   | Domain (Entities, Value Objects, Domain Logic)|   |   |   |
|   |   |   +-----------------------------------------------+   |   |   |
|   |   +-------------------------------------------------------+   |   |
|   +---------------------------------------------------------------+   |
+-----------------------------------------------------------------------+
```

### 1.1 Domain Layer (Core Business Rules)
* **Components:** Entities (e.g., `Vehicle`, `RentalSession`, `TestScenario`), Value Objects (`VIN`, `GeofenceCoordinates`, `SpeedLimit`, `BatteryLevel`), Domain Events (`DisengagementTriggered`, `RentalTerminatedEmergency`), and Pure Domain Services.
* **Constraints:** Zero third-party dependencies. No references to serialization formats, databases, HTTP protocols, or frameworks.

### 1.2 Use Case Layer (Application Business Rules)
* **Components:** Application services orchestrating business workflows (e.g., `StartAutonomousRentalUseCase`, `SimulateSensorFailureUseCase`, `IngestVehicleTelemetryUseCase`).
* **Boundary Interfaces (Ports):**
  * **Input Ports:** Defines driving operations exposed to controllers/consumers.
  * **Output Ports:** Defines secondary requirements implemented by infrastructure (e.g., `VehicleRepositoryPort`, `TelemetryPublisherPort`, `VehicleActuatorPort`).

### 1.3 Interface Adapters Layer
* **Driving Adapters:** HTTP/gRPC controllers, WebSockets for live telemetry dashboards, test scenario runner CLIs.
* **Driven Adapters:** Repositories implementing database persistence, message queue publishers/subscribers, CAN-bus/gRPC adapters targeting vehicle telemetry simulators.

### 1.4 Frameworks & Drivers Layer
* Fastify/gRPC servers, PostgreSQL/TimescaleDB drivers, NATS JetStream clients, mock telemetry emitters, OS-level utilities.

## 2. Tech Stack Decisions & Trade-Offs

| Category | Decision | Alternatives Considered |
| :--- | :--- | :--- |
| **Runtime / Language** | **Go (Golang 1.22+)** | Node.js / TypeScript, Python, Rust |
| **Primary Persistence** | **PostgreSQL 16 + TimescaleDB** | MongoDB, Pure PostgreSQL, Cassandra |
| **Messaging / Event Bus**| **NATS JetStream** | Apache Kafka, RabbitMQ, Redis Streams |
| **API & Transport** | **gRPC + Protobuf (Internal/Vehicle)** & **REST/OpenAPI (External Test API)** | GraphQL, REST-only |

### Pros & Cons Analysis

#### 1. Language: Go (Golang)
* **Pros:**
  * Native concurrency model (goroutines, channels) ideal for high-throughput simulated vehicle telemetry loops (e.g., 50–100 Hz per vehicle across hundreds of simulated cars).
  * High-performance compiled binary with small container footprint and deterministic memory footprint.
  * Explicit interface implementation natively enforces clean boundaries without class inheritance baggage.
* **Cons:**
  * Verbose error handling patterns.
  * Lacks advanced meta-programming compared to TypeScript or Python (intentional trade-off for maintainability).

#### 2. Storage: PostgreSQL with TimescaleDB Extension
* **Pros:**
  * Dual-purpose: ACID transactional guarantees for relational rental entities (`RentalSession`, `DriverProfile`) alongside hypertables for continuous, high-volume time-series telemetry (`Speed`, `DisengagementEvents`, `LidarHealth`).
  * Strong relational tooling, migration stability, and standard SQL interface.
* **Cons:**
  * Scaling writes to hundreds of thousands of events/sec requires aggressive hypertable partitioning and retention policies.

#### 3. Message Broker: NATS JetStream
* **Pros:**
  * Ultra-low latency, light resource utilization compared to Kafka.
  * Built-in support for pub/sub, at-least-once streaming, and request-reply paradigms needed for scenario triggers and vehicle actuation commands.
* **Cons:**
  * Smaller ecosystem of connectors compared to Apache Kafka.

## 3. Layer Dependency Inversion Rules

To prevent domain contamination and ensure testability of testbench scenarios without hardware or database availability:

1. **The Dependency Rule:** Dependencies must **only point inward**. Code in an inner circle can never know anything about code in an outer circle.
   * `Domain` MUST NOT import `Application`, `Adapters`, or `Infrastructure`.
   * `Application` MUST NOT import `Adapters` or `Infrastructure`.
   * Outer layers consume inner layers via concrete references; inner layers communicate with outer layers exclusively through **Ports** (interfaces).
2. **Persistence Ignorance:**
   * Entities do not contain ORM tags (e.g., no `gorm:"..."` or SQL annotations).
   * Data Mapping is mandatory: Database models (in `infra/postgres/models`) are converted to Domain Entities via mapper functions in the adapter boundary.
3. **Hardware / Simulator Decoupling:**
   * All hardware interaction (actuation, telematics, emergency brake disengagement) must be defined as an Output Port (e.g., `VehicleActuatorPort`).
   * The testbench must provide two adapter implementations: `SimulatedVehicleAdapter` and `HardwareCANVehicleAdapter`. The domain logic remains identical.
4. **Error Handling Boundaries:**
   * Infrastructure errors (e.g., `pq: connection refused`, network drops) must be caught at the adapter layer and translated into Domain/Application Errors (e.g., `ErrVehicleUnreachable`, `ErrPersistenceFailure`).

## 4. Directory Layout

The codebase follows the Standard Go Project Layout adhering to Clean Architecture principles:

```text
autodrive-testbench/
├── cmd/
│   ├── api/                    # HTTP & REST API entry point
│   ├── sim-runner/             # Autonomous testbench scenario runner CLI
│   └── telemetry-worker/       # Background ingestion & processing service
├── internal/
│   ├── domain/                 # Layer 1: Core Business Logic (Zero deps)
│   │   ├── entity/             # Vehicle, RentalSession, Scenario
│   │   ├── valueobject/        # Coordinates, Speed, TelemetryFrame
│   │   ├── event/              # DisengagementEvent, EmergencyStopEvent
│   │   └── error.go            # Domain-specific sentinel errors
│   │
│   ├── application/            # Layer 2: Use Cases & Application Interfaces
│   │   ├── port/
│   │   │   ├── in/             # Driving ports (Use case interfaces)
│   │   │   │   ├── rental_usecase.go
│   │   │   │   └── testbench_usecase.go
│   │   │   └── out/            # Driven ports (Repository & Service interfaces)
│   │   │       ├── vehicle_repo.go
│   │   │       ├── telemetry_publisher.go
│   │   │       └── vehicle_actuator.go
│   │   └── usecase/            # Concrete implementations of driving ports
│   │       ├── start_rental.go
│   │       ├── simulate_sensor_fault.go
│   │       └── process_telemetry.go
│   │
│   ├── adapter/                # Layer 3: Interface Adapters
│   │   ├── in/                 # Primary/Driving Adapters
│   │   │   ├── http/           # REST Handlers & DTO validation
│   │   │   ├── grpc/           # Telemetry RPC receivers
│   │   │   └── cli/            # Test scenario execution triggers
│   │   └── out/                # Secondary/Driven Adapters
│   │       ├── persistence/    # DB Repositories & SQL Mappers
│   │       │   ├── postgres/
│   │       │   └── timescaledb/
│   │       ├── messaging/      # NATS JetStream publishers/subscribers
│   │       └── vehicleclient/  # Mock Simulator & CAN-bus clients
│   │
│   └── infra/                  # Layer 4: Frameworks, Config, and Drivers
│       ├── config/             # Environment configuration parsing
│       ├── database/           # Connection pooling, migrations (e.g., goose)
│       ├── logger/             # Structured logger (zerolog/zap)
│       └── server/             # HTTP (Chi/Fiber) & gRPC server engines
├── proto/                      # Protobuf definitions for telemetry/control
├── migrations/                 # PostgreSQL & TimescaleDB schema migrations
├── test/                       # E2E test scenarios, mock profiles, and fixtures
│   ├── e2e/
│   └── scenarios/              # JSON/YAML simulated test cases (e.g., lidar_blindness.yaml)
├── Dockerfile
├── docker-compose.yml          # Local infra: Postgres, Timescale, NATS
├── go.mod
└── go.sum
```
